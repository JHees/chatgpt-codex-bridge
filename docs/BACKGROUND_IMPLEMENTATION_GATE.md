## 自动提交：当前实施缺口

现有 Loader 的公开 renderer interface 支持 settings、storage、events 和 allowlisted host commands，但没有输入区 accessory 或可见提交上下文的注册接口。

在当前 App 内部找到的 `setMessagePreparation` 是 App 启动时设置消息准备与排队策略的赋值入口，并非可追加、可卸载的插件注册入口。准备过程关联任务身份、排队/steer、权限、附件及开始请求的构造。本轮没有替换或包装它。

这不能证明所有 App 提交路径都不可适配，但尚不足以满足以下验收：

1. 点击、快捷键、输入法和重试只对应一次原生提交。
2. 可见 Bridge 说明与实际提交内容一致，正文和草稿不受破坏。
3. 新任务确认 ID 后才允许后台交流；导航不改变原请求归属。
4. 插件关闭、重载或异常后完整恢复原生提交行为。

因此按照实施计划停在入口验证阶段，不提前发布设置开关、不把“已启用”伪装为“已协作”，也不删除旧的可用收发实现。

## 下一步需要确认的范围

建议先授权一个独立的 Loader 通用输入区 interface 可行性任务，而不是直接承诺新增接口后一定可用：

- 输入区附加控件注册：提供明确的任务/草稿关联、挂载位置和卸载生命周期。
- 可见提交上下文注册：只附加用户可预览的文本，随一次原生提交关联回执；不得允许修改模型、权限或启动额外任务。
- Loader 用自己的示例包验证普通发送、排队、steer、输入法、重复提交和卸载恢复，不硬编码 Bridge 标识。

后台 Chat 适配仍归 Bridge，不迁入 Loader。若通用输入区 interface 仍需不可控地替换 App 私有发送逻辑，应报告不支持，而不是把同样的风险搬到 Loader 后宣称解决。

该跨仓库实施尚未获本轮授权；没有修改 Loader 源码。入口验证通过后才继续协作控制器、设置页、随包 skill、架构图和完整实机验收。
