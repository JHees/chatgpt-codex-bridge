# Bridge 实现复查

本文记录 `12a74ea` 的收发实现复查。后续已获授权的 Loader 修复和单包安装结果另见 [VALIDATION.md](VALIDATION.md)；本文中的“本轮”指该历史检查点。

## 结论

“一个 renderer 插件 + 一个 skill + Loader 已有命令入口”的边界适合当前单任务协作需求。没有必要恢复 daemon、MCP、项目读取服务或引入 SQLite 收发。真正需要加强的是收发状态、消息边界和安装后可用性，而不是增加层次。

当前版本号保持 `0.1.0`。本轮不修改 Loader，不改历史、tag 或远程仓库，也不自动部署运行副本。

## 已修正的问题

| 原实现问题 | 修正方式 |
| --- | --- |
| 同时调用可重复建 Chat；等待期间可被新轮次越过 | 每次只允许一个调用、一个未完成轮次 |
| 同 turn ID 换问题仍返回旧缓存 | 保存规范化请求，拒绝内容冲突；读缓存前核对页面身份 |
| `turn-1` 会匹配 `turn-10` 或 `turn-1:repair` | 精确的消息起始标记与边界，编码 ID 中的分隔符 |
| 扫描整个页面，可能采纳隐藏内容、草稿或用户引用 | 限定到对应用户消息与下一条用户消息之间，排除隐藏区域和用户内容 |
| 用回复文本去重，两个相同回复被视作一个 | 按 DOM 容器去重，保留独立重复块并报歧义 |
| 提取阶段过滤非法 JSON/错误 ID，导致修复逻辑收不到错误回复 | 提取候选块后再做严格协议校验；修复只针对可识别的块 |
| 第二次修复错误、发送不确定后仍能继续尝试 | 明确终止错误锁定本 session，允许安全 finish |
| reset 后等待中的 Promise 仍可能返回旧结果 | 控制器与 DOM 等待都使用实例代次检查 |
| 发送前可覆盖用户草稿，且只在首轮核对模型 | 每次发送检查空输入框、无生成状态、Medium/High 和输入内容/焦点 |
| 原会话 key 丢失时猜测另一个新 sidebar key | 删除替换猜测；锚点消失则停止，不重新打开别的 Chat |
| 超时错误包含 UI 标签和提示文本 | 仅返回计数和状态标志 |
| 安装后的 skill 引用未随包提供的仓库协议 | 随 skill 打包独立协议参考，统一超时/修复/终止规则 |

## 保留的实现边界

1. **DOM 仍然是兼容性边界。** 回复不依赖 Copy 按钮，但用户消息仍依赖 Edit 动作，导航/模型仍依赖中英文标签。没有声称规避所有 App 更新。
2. **生成结束是启发式。** 以生成控件消失和文本稳定判断；没有取得服务端完成事件。完全无结构的普通回复仍可能超时。
3. **返回原任务依赖 App。** Bridge 检查 Back 控件和会话锚点消失，只证明离开 Chat；没有独立的原任务 ID 校验。失败时要求手动恢复。
4. **不跨重载恢复。** 单 session 保存在内存，用户离开专用 Chat、实例重载或进程重启时停止，不从数据库猜测状态。
5. **Chat 不执行命令。** 插件只返回已验证的意图对象；是否执行、如何执行以及何时暂停仍由 Codex 和用户授权决定。

这些边界比模拟一个“稳定内部 API”更容易验证和维护。若未来 Loader/App 提供明确受支持的 Chat 消息接口，可只替换 DOM 适配器，保留当前协议与两个操作；本轮不预建这种接口或兼容层。

## 验证方法

先添加能在旧实现失败的回归用例，再修改生产代码。覆盖互斥、不可变轮次、终止状态、取消、精确标记、草稿保护、隐藏内容、重复回复、修复窗口、配置和返回检查。组合测试使用真实控制器与 DOM 适配器模拟一次错误回复、唯一修复、动作结果回传和 finish，确认重复读取不多发消息。
